# Schematic import

> **Changed in the Python-seam phase (2026-09-19).** `gtnh_schematics.py` and `gtnh_selections.py`
> are gone; Python no longer parses schematic files or scans regions. `mb_schematic_import` and
> `mb_schematic_build` call Java `baritone.schematic_import {path, origin?, includeAir?}`, and the
> selection tools are replaced by one `mb_copy(bounds, origin?, include_air?, at?, preview?, build?)`
> calling Java `baritone.copy {bounds:{min,max}, origin?, includeAir?}`. Both return the plan in the
> `baritone.build_preview`/`baritone.build` spec shape plus `size:[w,h,l]`, `count` and
> `skipped:{air,unknown}` (import) or `tileEntities` (copy); the Python wrappers only strip those
> report fields, apply explicit overrides and forward to preview/build. The file-format details
> below describe the Java importer's inputs; the Python CLI paths in this document no longer exist.

`tools/mcp/gtnh_schematics.py` converts canonical JSON, legacy MCEdit
`.schematic`, Sponge v1/v2 `.schem`, and Litematica v4 `.litematic` files into
the explicit-cell request consumed by the GTNH construction builder. NBT may be
gzip-compressed or plain. Importing is read-only; it does not contact Minecraft.

```powershell
python tools/mcp/gtnh_schematics.py house.schematic --origin 120 70 -35 `
  --registry legacy-block-ids.json > house-build.json
```

An extensionless name tries `.schematic`, `.schem`, `.litematic`, then
`.json`. `--schematic-directory` restricts this lookup to a bare filename;
multiple matching extensions are rejected as ambiguous.

The registry file is a JSON object such as
`{"1":"minecraft:stone","300":"gregtech:gt.blockmachines"}`. Legacy numeric
IDs are save/modpack-specific. The importer uses an embedded
`SchematicaMapping` when present and requires this explicit map for every other
non-air numeric ID. It never interprets a numeric world ID as a stable registry
name. `Blocks`, `Data`, and packed `AddBlocks` use bundled Baritone's ordering
(high nibble for the even cell, low nibble for the odd cell), and `Materials`
must be `Alpha`.

That nibble order was independently checked against the official
[Lunatrius Schematica `SchematicAlpha` reader and writer](https://github.com/Lunatrius/Schematica/blob/master/src/main/java/com/github/lunatrius/schematica/world/schematic/SchematicAlpha.java):
the writer stores `(extra[even] << 4) | extra[odd]`, and its reader reverses that
operation. The test fixture contains four fixed high IDs across both nibble
positions; it does not round-trip bytes generated by this importer.

Python integration is deliberately independent of MCP registration:

```python
from gtnh_schematics import import_schematic

imported = import_schematic(
    "house.schematic", origin=[120, 70, -35],
    registry={1: "minecraft:stone", 300: "gregtech:gt.blockmachines"})
canonical_request = imported["build"]
preview = kernel.call("baritone.build_preview", **canonical_request)
job = kernel.call("baritone.build", **canonical_request)
# After correcting access or materials for a retained blocked job:
kernel.call("baritone.resume", jobId=job["jobId"])
```

`build` contains `origin`, explicit `cells`, `replaceExisting`, `timeoutTicks`,
and `overrideProtection`, plus validated optional `size`, `mode`, `settings`,
`allowBreak`, and `allowPlace`. Canonical JSON can also specify item selectors,
placement hints, replacement predicates, and verification predicates on cells. Item `nbt`
is an exact SNBT string, matching the native selector contract. Placement accepts
native integer faces 0--5 or the documented names down/up/north/south/west/east;
names are emitted as their native integers. Other placement fields are `hit`
(three values in -16..16), `yaw` (-360000..360000), `pitch` (-90..90), and the
boolean `verifyAfterPlacement`. `sneak` is not a native placement field and is
rejected rather than silently ignored. `timeoutTicks` is 1--72,000.

A cell may independently specify `verify:{pickedItem:{id,meta?,nbt?,ore?}}`.
This adds a native `getPickBlock` stack predicate to the block ID/metadata check,
which distinguishes machine or pipe variants that share a world block state.
`item` remains the selector for what the player holds during placement; it is
never copied into `verify` or treated as proof of the resulting variant. A
matching picked item proves only that predicate; it does not prove that machine
configuration, inventory, ownership, energy, or multiblock state was captured.
During selection copy, an explicitly observed native `placementItem` is preserved
as `cell.item` only when the bridge established that it is an `ItemBlock` whose
block matches the observed world block. An arbitrary `pickedItem`, including a
non-block mod pick result, is never promoted into placement material.

For an observed item variant, `nei.item` reports `placement.blockId` and
`placement.initialBlockMeta`. The latter is the native initial block metadata
derived from that item, and is distinct from the item's own variant metadata.
Face, player pose, and post-placement callbacks may still change the final block
state, so use this metadata to prepare a candidate cell and verify the actual
placed block and any independent `verify.pickedItem` condition afterward.

Air is omitted by default; `--include-air` emits explicit clearing cells. After
filtering, a blueprint request must contain 1--16,384 cells. Explicit
`mode:builder` imports allow up to 1,048,576 cells; the GTNH MCP wrappers upload
plans above 4,096 cells in guarded stages. Local position and origin Y
are each limited to -255..255, and every translated cell must be inside native
world bounds (X/Z ±30,000,000 and Y 1..254). A legacy schematic whose base is at
Y zero therefore needs an explicit usable `--origin`.

Legacy `TileEntities` are preserved under `requirements` with their local
position and full decoded NBT. Each is marked unsupported and requires a
mod-specific placement/configuration adapter. The NBT is never attached to a
normal placement cell, so importing a machine cannot silently claim to restore
its inventory, energy, owner, or running state. Legacy `Entities` are likewise
preserved as unsupported entity-adapter requirements. Canonical JSON rejects
unknown document and cell fields, including embedded tile NBT, so unsupported
state cannot disappear through a misspelled or unhandled property.

The parser limits compressed files to 32 MiB, decompressed data to 128 MiB,
source volume to 16,777,216 blocks, NBT nesting to 64 levels, and output to the
mode-specific explicit-cell limit. Parsed NBT lists and numeric arrays share a 262,144-object
element budget. NBT byte arrays remain compact bytes while parsing, so large
`Blocks` and `Data` arrays do not expand into one Python integer object per byte;
small byte arrays inside unsupported NBT requirements are converted only at the
bounded JSON-extension boundary. That conversion has one shared 64 KiB encoded
budget for the complete requirement, including nested container/key overhead;
individually small arrays cannot multiply the allocation beyond the bound. It
rejects truncated data, trailing NBT, duplicate JSON
positions, inconsistent arrays, palette conflicts, invalid metadata and tile
entities outside the source dimensions. Rotation and mirroring are rejected
because changing positions without remapping metadata/block state would rotate
many blocks incorrectly.

Sponge `BlockData` is decoded as the complete unsigned-varint stream in
Baritone's Y-Z-X order. Truncated, overlong, out-of-range, and trailing varint
bytes are rejected. Litematica uses version 4's continuous little-endian packed
longs, including entries split across two longs. Regions are decoded
independently; negative sizes use the lower region corner, all regions share the
enclosing minimum corner, and later overlapping regions replace earlier cells.
Packed array lengths and palette indexes are exact.

A property-free palette value preserves its registry name and is emitted with
metadata zero. Use an explicit mapping whenever metadata zero is not known to be
the correct 1.7.10 state. Any serialized state with properties needs an explicit `--palette` JSON mapping.
Sponge keys are matched exactly. Litematica keys use the block name followed by
properties sorted by name, such as `mod:machine[active=true,facing=north]`.
Mapped values use canonical cells, for example
`{"id":"mod:machine","meta":3}`, and may include validated `item` and
`placement` and `verify` objects. The importer does not guess modern flattening,
property-to-metadata mappings, or state rotation.

Imported NBT builds carry their positive source `size`. Canonical JSON may also
provide `size`, `mode` (`blueprint` or `builder`), and a validated `settings`
object. Supported settings cover the native layer, repeat, map-art, placement,
inventory, registry-ID substitution, metadata-mask, and throwaway-item options.
Unknown setting names and malformed nested values are rejected.

The GTNH profile exposes `mb_selection` for world/dimension-scoped pos1/pos2,
ordered multi-region add/remove/clear/undo, and all/newest/oldest transforms.
Copy reads every selected cuboid through paged all-state scans; unloaded or
incomplete pages fail rather than becoming air. Selected air remains an explicit
clear cell, while gaps between selection regions remain absent. Paste preserves
the copy anchor offset and defaults to a read-only builder preview. Tile-bearing
blocks retain an unsupported requirement and block paste unless copy explicitly
uses `block_states_only:true`, which records the intentional omission of machine
configuration. Copy also preserves the scan's native picked-item identity as an
independent `verify.pickedItem` predicate when available; this still does not
capture or recreate tile NBT or machine configuration. When the scan separately
reports a verified `placementItem`, copy also retains its exact item metadata and
NBT as the placement selector. For example, a GT machine can have block metadata
`1` while both its placement item and picked-item verification use variant `511`.
`mb_builder_pause` returns a terminal paused receipt for its call, while the
durable job continues through `mb_work_resume`; `mb_builder_materials` reads its
material summary.

## Relationship to the existing builders

The importer follows original Baritone's MCEdit dimensions, linear index
`(y * length + z) * width + x`, `Materials` check, gzip NBT input, and exact
`AddBlocks` nibble order. Original `BuilderProcess` discovers mismatches, searches
reachable placement faces, checks the held `ItemBlock`, and replans until
complete. The GTNH endpoint retains that player-driven behavior. Blueprint mode,
and builder mode with `settings.restricted:true`, restrict edits to explicit cells;
an unrestricted builder with `allowBreak` or `allowPlace` may edit nearby access
terrain under its protection and inventory rules. See
[CONSTRUCTION_PARITY.md](CONSTRUCTION_PARITY.md) for the full contract.

The DJ2 blueprint bridge established the lifecycle pattern reused here: preview,
inventory/conflict preflight, tick and stall bounds, retained job IDs, resume from
a fresh diff, temporary-setting cleanup, and independent verification. The
importer only decodes and validates files; Java owns execution, reachability,
materials, recovery, and verification.

The deliberate differences are portable registry names instead of original
Baritone's process-local numeric registry lookup, bounded blueprint/builder limits instead
of DJ2's 4,096-cell blueprint limit, and explicit unsupported tile-NBT
requirements instead of silently discarding machine state.
